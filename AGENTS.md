# Repository Guidelines

Cowork is a GPUI desktop app for collaborating on LLM agent threads (Ollama, through the workspace's own agent stack), with peer-to-peer sharing over iroh. Rust 2024 Cargo workspace.

## Project Structure

- `crates/cowork` — the app, as a library with a thin binary (`src/main.rs` calls `cowork::run`) so examples can reach its components. `src/lib.rs` holds the `Cowork` view struct, app startup, and top-level rendering; the rest of `Cowork`'s methods are `impl Cowork` blocks in the module for their area.
  - State: `thread.rs` (`Thread`, private participant identity/membership, model catalog and ownership, per-peer draft generations, and host-event internals; narrow maintenance APIs outside the thread subtree), `thread_draft.rs` (`ThreadDraft`, nested as `thread::draft` though the file remains here; the draft, separate editor cache, and presence), `thread/permissions.rs` (host-owned peer modes, live defaults and overrides, typed closure-scoped `Authorized` guards), `timeline.rs` (messages and their wire form), `timeline_projection.rs` (placing a run's output and operational state in its agent message), `transcript.rs` (the transcript, a replica of the host's agent session's conversation: its wire form, and folding the session's run events into a thread), `models.rs` (providers and model catalogs, and each model's `Reasoning`), `providers.rs` (connecting to Ollama, Anthropic, and OpenAI: Anthropic's and OpenAI's API keys, kept in the OS keychain through GPUI's credentials API and never sent to peers; discovering each provider's models into its part of the catalog, OpenAI's from a built-in list with their context windows; and `ModelProvider::request_parameters`, the one place for provider-specific request parameters such as Ollama's `num_ctx`, Anthropic's `max_tokens` and thinking style, and OpenAI's `reasoning_effort`).
  - Sharing: `protocol.rs` (wire messages; postcard, length-delimited frames, control vs. bulk queues), `sharing.rs` (hosting, joining, and handling collaborators' requests, nested as `thread::sharing` though the file remains here), `participant.rs` (`ParticipantId` and derived names/colors), `profile.rs`.
  - Agent runs: `submission.rs` (which submission wins, and the prompt, nested as `thread::submission` though the file remains here), `generation.rs` (running the agent, nested as `thread::submission::generation` though the file remains here: one `agent::AgentSession` per local or hosted thread (`ThreadAgent`), created with its first run and kept for later ones; its definition (model, system prompt, tools, thinking, `num_ctx`), the `environment` context section telling the model the project's paths and mode whenever they changed, compaction requests when usage passes the threshold, and relaying the session's events to everyone as `RunEvent`s; Cowork keeps its own pending-submission queue and hands the session one queued input at a time, while steers go to the running session's steering lane and leave the pending list only on its commit or `Removed` receipt), `tool_approval.rs` (`CoworkHost`, the session's `AgentHost`, and `CoworkInput`, its input: the always-allowed tool list, registering a committed steer's comment aliases, authorizing every other call on its `sandbox::Needs`, the unattended policy of scheduled runs, and deciding waiting calls), `prompt.rs` (the content of a submission's prompt). The system prompt is `prompts/system.md`, compiled in with `include_str!`; `generation.rs` appends the host's platform. The runtime owns the compaction prompt. Tool definitions and the system prompt never vary within a session, keeping the prompt prefix cacheable; what changes goes in the environment note.
  - UI: `composer.rs`, `draft_editing.rs`, `composer_attachments.rs`, `project_folders.rs` (the bottom bar's project folders: the host's add button and per-folder menu, names only for collaborators; keeps the thread's sandbox project in step, a change applying from the next command; `ProjectFolders` is also the schedule dialog's picker), `project_mode.rs` (the project's `Read`/`Write`/`Write + Network` mode (`ProjectMode::Network`) and its bottom bar menu, with warnings on the last two; host-only, mirrored, defaults to `Read`; the access commands run with unless they ask for their own), `timeline_view.rs`, `inline_icons.rs` (the Markdown plugin drawing `![alt](icon:name)` as the app's icon for a feature, in every timeline text view), `timeline_virtualization.rs` (`VirtualTimeline`, full virtualization of the timeline inside its scroll container: only rows near the view, and pinned ones, are built; heights measured when drawn and kept in `TimelineLayout`, rows never drawn counting as the average, with the scroll offset compensating so what is on screen stays put; planning each frame's rows from the thread in place, cloning only rows that are built; see `docs/timeline-performance.md`), `timeline_selection.rs` (selection across the virtualized timeline: the rows holding a selection's ends stay built while it lasts, and Copy of a selection spanning rows is built from the rows between them, `Cowork::copy_pieces` in `timeline_view.rs` listing what each row draws; `PromptText`, a prompt's selectable text recording what of it is selected), `pending_view.rs` (pending submissions, shown as timeline rows), `context_settings.rs` (the context window and compaction threshold, saved by `settings_file.rs`, and the composer's context details), `theme.rs`, `model_picker.rs` (the picker, and providers' names and logos: monochrome logos drawn in the theme's text color, Anthropic's in its own), `peer_access.rs` (nonmodal titlebar sharing popover with link/sharing actions, host default modes and per-peer overrides, and collaborator access display), `top_bar.rs`, `sidebar.rs`, `archive.rs` (archiving the user's own threads from the sidebar, which ends their run and sharing; the archive page restoring or permanently deleting them, deletion also removing their folder, while the profile's statistics keep counting deleted ones), `schedules.rs` (the Scheduled page listing scheduled tasks with their schedule, status, and last run, and the dialog creating and editing them with their run history; see `docs/schedule.md`), `search_palette.rs`, `settings.rs` (`SettingsPage`, one variant per settings tab, each with its center stage page; the sidebar shows the settings view, with "Back to app" and the tabs, exactly while `MainStage::Settings` is showing, and the profile button opens it on Profile), `profile_page.rs` (the Profile settings page), `provider_setup.rs` (choosing a provider and then one of its models, with an API key field above the models of providers that need one, with `ProviderStep` for the step and `ProviderSetupPlace` for where it shows: the welcome screen picks for the active thread, while the Providers settings page picks new chats' model and can always refresh models), `welcome.rs` (the welcome screen's greeting and first-chat button around those steps), `avatars.rs`, `caret.rs`, `highlight.rs`, `assets.rs`, `tool_call_card.rs` (the card asking whether a tool call may run; tools may pass their own body), `file_change_view.rs` (a `write_file` or `edit_file` call as a gpui-component `Diff` with a Diff / JSON switch, the approval card's body and the timeline row's details; every peer computes the patch from the call's arguments with `similar`: an edit's `old_string` to `new_string`, a write's whole content as added), `component_preview.rs` (a fullscreen dev window showing components in their states in a grid, opened by `examples/component_preview.rs`; `examples/compaction_preview.rs` opens the compaction settings and context UI; the grid includes `write_file` and `edit_file` cards with their diffs).
  - Scheduled tasks: `scheduled_task.rs` (a task's settings, when it is due including custom RRULEs, the missed-run and one-queued-run policy, and run history; pure data, tested without an app), `scheduler.rs` (looking at the clock, the one-at-a-time queue, submitting runs through `submit_scheduled_prompt`, the approval notification, and saving tasks to `~/.cowork/schedules.json`). Scheduled runs refuse a tool call needing approval the first time and ask on an identical repeat (`tool_approval.rs`).
  - Other: `attachments.rs` (reading and classifying files), `usage.rs` (token usage and the activity chart), `settings_file.rs` (saving the user's settings to `~/.cowork/settings.json` whenever one changes: the model new chats start with and the context settings; only loading and saving, while `Cowork::open_start_stage` in `lib.rs` decides what a launch opens on: onboarding (`thread/onboarding.rs`) exactly when the user has no threads, open or archived, starting on its own once a selected model is discovered, and otherwise a new chat, with or without a model), `statistics.rs` (saving what the profile page's statistics count of deleted threads to `~/.cowork/statistics.json`; the rest is added up from the saved threads), `thread_files.rs` (saving the host's own threads in `~/.cowork/threads/<thread id>/`: `thread.json` with Cowork's own records, `messages.jsonl` with the transcript's agent records, only appended to, `attachments/`, and the commands' `scratch/`; saved at turn boundaries and read back at startup, checked as a `Welcome` snapshot; drafts aren't saved; one instance holds the lock, others save nothing; see `docs/collaboration.md` "Saved threads").
- `crates/draft` — the collaborative draft as a Yrs CRDT document (prompt blocks, comments, attachment records) plus `verify_change` validation. No GPUI or networking dependencies; keep it that way.
- `crates/agent` — the agent stack in one crate (see its `README.md`): it re-exports `crates/agent-runtime` (sessions, definitions, hosts, requests, context sections, compaction, the conversation; see `docs/agent-architecture.md`) at its root, `crates/language-model` (owned messages, versioned envelopes, the provider contract) as `agent::model`, `crates/tool-runtime` (typed tools with a `Context` and per-call `Access`) as `agent::tool`, and the provider clients in `crates/providers/*` (`agent::Ollama`, ...; the HTTP ones share `crates/provider-sse`). `crates/agent-input` has the inbox's delivery lanes. Cowork depends only on `agent`.
- `crates/tools` — tools exposed to the model (`respond_to_comment`, whose context is the host's `RunComments`, and `calculate`).
- `crates/sandbox` — the `run_command` tool and the file tools, whose context is the thread's `ThreadSandbox` and whose access is `Needs` (`src/context.rs`): the agent's shell commands run on the host with its own shell, tools, and login shell environment (`src/environment.rs`, captured by running the app with `--printenv` in a login shell), each contained by the OS sandbox through mxc-sdk (Seatbelt, Bubblewrap, a Windows process container). Every setting (project folders at their real paths, read-only unless writable; a per-thread scratch folder as `TMPDIR`, in the thread's folder, and where commands start without project folders; the real `HOME`, so `~` matches granted folders; read-only tool folders and git settings (`~/.gitconfig`, `~/.config/git`); on Windows, every drive read-only as Codex does, since `git` and others need the folders above a project; denied credential paths; no network except with `network` access, outbound only; no time, output, or resource limits) is documented in `src/settings.rs`; keep it the single place to read them. `src/project.rs` has `Project` and folder naming; each command uses the project as it is when it starts. A call runs with the mode's `sandbox::Access` unless its `access` argument asks for its own, and may name host folders outside the project in `read_folders`/`write_folders`, for that command only (how the agent asks for higher permissions). The `request_permissions` tool (`src/permissions.rs`) asks for either for the rest of the run, as Codex's tool of that name; once allowed, running it adds them to the thread's run grants (`Sandboxes::run_grant`), which later commands get. `src/grant.rs` has `Grant`/`Folders`: resolving the folders the model names (absolute or `~/`, existing, never a denied credential path), and whether one grant covers another. A call's `Needs` are computed from its arguments before it runs; `ThreadSandbox::covers` says whether they are within the project's mode and folders and the run's grants, so the call runs without approval; every other call waits, and only the host may allow it (`tool_approval::HOST_ONLY`). A command runs with what it asked for, or the mode or run grant as they are when it starts (`ThreadSandbox::command_grant`). Sessions run calls one at a time. `cargo test -p sandbox` runs real contained commands in milliseconds.
  - The file tools (`src/files.rs`: `list_directory`, `read_file`, `view_image`, `write_file`, `edit_file`) work from the host process rather than a sandboxed command. `view_image` sends small PNG/JPEG files as they are and otherwise decodes, orients, and scales images down to 2048 px (JPEG for photos); models that don't accept images get a note in its place from the agent runtime (`agent-runtime/src/model.rs`), based on the catalog's `ModelInfo::image_input`. Every path they accept (`<folder name>/…`, `scratch://…`, absolute paths, `.` for the list) and every check (named and `scratch://` paths staying inside, absolute paths readable anywhere, denied credential paths, writes only to a writable project or scratch) is in `src/paths.rs`; keep it the single place that maps a model's path to a host file. Listing, reading, and viewing images are always allowed; `write_file` (create or replace a whole file) and `edit_file` (replace exact text, once or with `replace_all` every occurrence) run without asking in `Write` and `Write + Network`, and wait for the host's approval in `Read`.
- `docs/collaboration.md` — the spec for collaborative drafts, the document layout, protocol, and host validation. Read the relevant section before touching draft sync, presence, submission, or attachment transfer, and update it (including its "Status" section) when behavior changes.
- `TODO.md` — the owner's feature notes; don't edit unless asked.

## Build, Test, and Development Commands

- `cargo run -p cowork` — run the app. Agent runs need a local Ollama server.
- `cargo run -p cowork --example component_preview` — open the component preview, to review components in states the app can't reach yet (`--example compaction_preview` for the compaction UI).
- `cargo test --workspace` — all tests.
- `cargo test -p draft` / `cargo test -p cowork <name>` — narrower runs.
- `cargo fmt --all` — default rustfmt settings; the tree is currently fmt-clean.
- `cargo clippy --workspace --all-targets` — the tree has some existing warnings; don't add new ones.

There is no CI; run fmt, clippy, and the tests yourself before finishing.

For Python scripting, use the `uv` package manager.

## Code Style and Conventions

- Dependencies are declared once in the root `Cargo.toml` `[workspace.dependencies]` and used as `foo.workspace = true`. Every crate has `[lints] workspace = true`.
- Visibility inside the `cowork` crate uses `pub(crate)`; only `run` and `component_preview` are public, for the binary and the example.
- Doc comments explain intent, invariants, and why (see `protocol.rs`, `draft/src/lib.rs`). Keep that style when adding types and constants.
- Text offsets in the draft API and in comment targets are UTF-8 byte offsets on char boundaries.

## Architecture Constraints

- The host is authoritative. All traffic goes through it; collaborators never talk to each other. The host's own edits, submissions, stops, and model changes go through the same code paths as a collaborator's.
- Local and shared threads use the same Yrs-backed draft. A local thread just has no peers.
- Yrs transactions are synchronous, live in the GPUI `Thread` entity, and must never be held across an `await`. Only encoded bytes cross to the Tokio runtime (`TOKIO_RUNTIME` / `tokio_handle.spawn`). Results come back to GPUI via `cx.spawn`/`spawn_in`.
- Draft invariants (in `docs/collaboration.md` "Validation" and `draft/src/validate.rs`): `creator` and `target` are write-once, attachment records and comment targets are atomic `Any` values, and `order`/`items` change together in one transaction. Changing the document layout means updating `validate.rs` and the spec as well.
- Updates merged with `Draft::apply_update` are never re-emitted as local updates. Don't break that; it prevents echoing other participants' edits.

## Making Changes

- **Protocol**: bump `PROTOCOL_VERSION` in `crates/cowork/src/protocol.rs` on any change to wire messages or to model identifier semantics, and on any change to the agent's records that travel (`agent::persistence::record`'s entries and compactions, and the message envelope). Never change the encoding of `CollaboratorMessage::Join` or `HostMessage::Rejected`: keep their variant index, and keep `Join`'s version as its only field. `version_handshake_encoding_is_stable` checks this. The wire needs no backward compatibility beyond that.
- **Saved files**: saved threads (`thread_files.rs`), statistics, and schedules have their own format versions, independent of `PROTOCOL_VERSION`: a wire change only needs `thread_files.rs`'s in-memory conversion to the `Welcome` snapshot updated. Bump a file's `FILE_VERSION` when its format changes incompatibly (and when the agent's records in `messages.jsonl` change); files of another version are left unread and untouched, so either convert old ones or accept losing them.
- **GPUI pins**: `gpui`/`gpui_platform` (the `gpui-pre`/`gpui-pre-platform` packages) are pinned to match the GPUI snapshot the gpui-kit release (`gpui-component` and friends) pins. Upgrade them together, never one alone.

## Testing

- Unit tests live next to the code in `#[cfg(test)] mod tests`. `draft` keeps its larger suite in `crates/draft/src/tests.rs`, grouped by numbered section comments and using its helpers (`replica_of`, `sync`, and so on) to simulate multiple replicas.
- In `cowork`, UI and entity tests use `#[gpui::test]` (with gpui's `test-support` dev feature), and async protocol tests use `#[tokio::test]`. Tests don't need a running Ollama server or network.
- Tests that drive the whole app (a `Cowork`, threads, or a host and collaborator pair) are in `crates/cowork/src/tests/`, one file per area, with the shared helpers (`test_cowork`, `composer_test_cowork`, `Collaboration`, and so on) in `tests/mod.rs`. Test helpers needed by modules outside `tests/` are in `test_support.rs`. A host's run events are scripted with `test_support::ScriptedHost`, which numbers committed entries as the host's session does; agent sessions themselves are tested with a scripted `LanguageModelProvider` (see `generation.rs`).
- Test each behavior once, at the lowest level that can observe it: rules in unit tests next to the code, and app tests in `tests/` only for the wiring between parts (one case, not every mode or variant). Prefer extending an existing test to adding a new one.
- Don't test constants, labels, defaults, derived schemas, or what a library already guarantees, and don't pin cosmetic layout (exact pixels, alignment); layout tests are for real bugs such as overlap, clipping, or the layout jumping.
- Add a regression test for a bug fix when the bug was subtle and no existing test could have caught it, especially convergence cases in `draft`. New wire messages go in `protocol.rs`'s existing round-trip test rather than a new one.
